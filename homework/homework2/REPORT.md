
# Отчёт по домашней работе №2 – Паттерны проектирования

## a) Общая идея решения и реализованный функционал

Цель — реализовать модуль «Учет финансов» для условного ВШЭ-Банка, с упором на:

- качественную доменную модель (`BankAccount`, `Category`, `Operation`);
- применение паттернов GoF;
- соблюдение SOLID и GRASP.

### Реализованный функционал

1. **Работа с доменной моделью**
   - Счета (`BankAccount`)
     - создание счёта с начальным балансом или без (`BankAccountService.create(...)`);
     - изменение баланса за счёт проведения операций;
     - просмотр списка счетов (через консольное приложение);
     - хранение в `BankAccountRepository` / `InMemoryBankAccountRepository`.
   - Категории (`Category`)
     - создание категорий двух типов: `INCOME` и `EXPENSE` (`CategoryService.create(...)`);
     - переименование;
     - просмотр списка категорий;
     - хранение в `CategoryRepository` / `InMemoryCategoryRepository`.
   - Операции (`Operation`)
     - создание операций дохода и расхода (`OperationService.create(...)`);
     - обновление операций (`OperationService.updateOperation(...)`);
     - удаление операций (`OperationService.delete(...)`);
     - пересчёт баланса счёта при добавлении/изменении/удалении операций;
     - хранение в `OperationRepository` / `InMemoryOperationRepository`.

2. **Аналитика**
   - `AnalyticsFacade.netForPeriod(from, to)`
     - считает сумму доходов, расходов и разницу за период.
   - `AnalyticsFacade.groupByCategory(from, to)`
     - группирует операции по категориям;
     - суммирует значения по каждой категории (с учётом типа: доход/расход).

3. **Импорт и экспорт данных**
   - **Импорт**
     - импортеры:
       - `CsvImporter`
       - `JsonImporter`
       - `YamlImporter`
     - фасад `ImportFacade.importOperations(Importer, Path)`:
       - читает файл;
       - парсит данные в список `Map<String, Object>`;
       - по каждой записи создаёт `Operation` через `OperationService`.
   - **Экспорт**
     - `ExportVisitor` + реализации:
       - `CsvExportVisitor`
       - `JsonExportVisitor`
       - `YamlExportVisitor`
     - экспортируют коллекции `BankAccount`, `Category`, `Operation` в соответствующие строковые форматы.

4. **Пересчёт балансов**
   - `OperationService.recalculateAllBalancesFromHistory()`:
     - обнуляет балансы всех счетов;
     - сортирует операции по дате;
     - последовательно применяет их, заново рассчитывая баланс.

5. **Измерение времени сценариев**
   - Паттерн Command:
     - `CreateAccountCommand`
     - `CreateCategoryCommand`
     - `AddOperationCommand` и др.
   - Паттерн Decorator:
     - `TimedCommandDecorator` измеряет время каждого сценария и пишет его в `MetricsCollector`.
   - В `ConsoleApplication` все сценарии запускаются через `TimedCommandDecorator`, поэтому для каждого пункта меню можно собрать статистику по времени выполнения.

6. **UI и запуск**
   - Консольное приложение `ConsoleApplication`:
     - текстовое меню;
     - диалог с пользователем через `Scanner`;
     - запуск команд.
   - `Main` содержит только:
     - поднятие Spring-контекста (`AnnotationConfigApplicationContext(AppConfig.class)`);
     - получение `ConsoleApplication` из контекста и вызов `run()`.

## b) SOLID и GRASP: какие принципы реализованы и где

### SOLID

**S — Single Responsibility Principle**

- `BankAccount`, `Category`, `Operation`  
  Только доменные данные и простое поведение без знания инфраструктуры.
- `DomainFactory`  
  Только создание/валидация доменных объектов.
- `BankAccountService`, `CategoryService`, `OperationService`  
  Только бизнес-логика и работа с репозиториями.
- `AnalyticsFacade`  
  Только аналитика по операциям.
- `ImportFacade`  
  Только импорт данных и преобразование сырых записей в доменные операции.
- `ConsoleApplication`  
  Только консольный UI и «склеивание» сценариев с услугами сервиса.

**O — Open/Closed Principle**

- Добавление новых форматов импорта/экспорта не требует изменения доменных классов:
  - новый формат импорта → новый наследник `Importer`;
  - новый формат экспорта → новый `ExportVisitor`.
- Новые сценарии работы в консоли можно добавлять через отдельные `Command`, почти не трогая остальной код.

**L — Liskov Substitution Principle**

- Наследники `Importer` (`CsvImporter`, `JsonImporter`, `YamlImporter`) подставляются вместо базового `Importer` без изменения логики `ImportFacade`.
- Реализации `ExportVisitor` подставляются вместо интерфейса в `ConsoleApplication`.

**I — Interface Segregation Principle**

- Отдельные интерфейсы репозиториев:
  - `BankAccountRepository`
  - `CategoryRepository`
  - `OperationRepository`  
  Каждый решает свои задачи, клиенты не зависят от «лишних» методов.
- `Command`, `Exporter` (`ExportVisitor`), `Importer` — небольшие и специализированные интерфейсы.

**D — Dependency Inversion Principle**

- Высокоуровневые модули зависят от абстракций:
  - сервисы зависят от интерфейсов репозиториев, а не от конкретных in-memory реализаций;
  - `ImportFacade` зависит от абстрактного `Importer`, а не от конкретного формата;
  - `ConsoleApplication` зависит от интерфейсов/сервисов/фасадов, а конкретные реализации создаются в `AppConfig`.
- Конфигурация зависимостей вынесена в Spring-конфиг (`AppConfig`), а не зашита через `new` в бизнес-логике.

---

### GRASP

**High Cohesion**

- Классы сфокусированы:
  - `BankAccountService` отвечает за бизнес-операции со счетами;
  - `AnalyticsFacade` — за агрегацию данных и расчёты;
  - `ImportFacade` — за импорт;
  - `ConsoleApplication` — за диалог с пользователем и запуск команд.

**Low Coupling**

- UI (`ConsoleApplication`) не знает деталей хранения данных — он работает через сервисы и фасады, которые в свою очередь используют репозитории через интерфейсы.
- Доменные классы не зависят от Spring, консоли, импорта/экспорта.

**Controller**

- `ConsoleApplication` реализует GRASP Controller:
  - принимает пользовательский ввод;
  - выбирает соответствующий сценарий;
  - дергает доменные сервисы и фасады.

**Indirection**

- Использование промежуточных слоёв (сервисы, фасады, фабрика) снижает прямую связь между слоями:
  - UI → сервисы/фасады → репозитории/домены;
  - импортеры → фасад → сервисы → домены.

## c) Использованные паттерны GoF: что, где и зачем

Ниже перечислены ключевые паттерны, реализованные в проекте.

### 1. Фабрика (Factory)

- **Класс:** `DomainFactory`
- **Где используется:**
  - `BankAccountService` при создании счетов;
  - `CategoryService` при создании категорий;
  - `OperationService` при создании операций.
- **Зачем:**
  - общее место создания доменных объектов;
  - единая валидация (например, `amount > 0` для `Operation`);
  - исключение дублирования логики и разбросанных по коду `new`.

---

### 2. Фасад (Facade)

- **Класс:** `AnalyticsFacade`
  - предоставляет методы:
    - `netForPeriod(from, to)`
    - `groupByCategory(from, to)`
  - внутри работает с репозиторием операций и доменной логикой.
- **Класс:** `ImportFacade`
  - метод `importOperations(Importer, Path)`:
    - читает сырые данные;
    - преобразует их в `Operation` через `OperationService`.

**Зачем:**

- упростить использование сложной подсистемы (аналитика, импорт) внешним кодом;
- предоставить один «вход» для сценариев, скрыв детали внутренней реализации.

---

### 3. Шаблонный метод (Template Method)

- **Абстрактный класс:** `Importer`
  - метод `importAsListOfMaps(Path)`:
    - читает файл в строку;
    - вызывает `parse(raw)`.
  - `parse(raw)` — абстрактный метод, реализуемый в наследниках.

- **Наследники:**
  - `CsvImporter`
  - `JsonImporter`
  - `YamlImporter`

**Зачем:**

- общая часть алгоритма (чтение файла) реализуется один раз;
- различающиеся части (парсинг JSON/YAML/CSV) выносятся в подклассы.

---

### 4. Посетитель (Visitor)

- **Интерфейс:** `ExportVisitor`
  - `exportAccounts(...)`
  - `exportCategories(...)`
  - `exportOperations(...)`

- **Реализации:**
  - `CsvExportVisitor`
  - `JsonExportVisitor`
  - `YamlExportVisitor`

**Зачем:**

- добавлять новые форматы экспорта можно через новые реализации `ExportVisitor`, не изменяя домены;
- сериализация отделена от бизнес-логики и доменной модели.

---

### 5. Команда (Command)

- **Интерфейс:** `Command`
  - метод `execute()`.

- **Реализации:**
  - `CreateAccountCommand`
  - `CreateCategoryCommand`
  - `AddOperationCommand`
  - (дополнительные команды могут быть добавлены по аналогии).

- **Где используется:**
  - в `ConsoleApplication`: для каждого пункта меню создаётся соответствующая команда, которая затем выполняется.

**Зачем:**

- каждый пользовательский сценарий превращён в объект;
- удобно навешивать дополнительное поведение (логирование, измерение времени — через Decorator);
- команды легко тестировать отдельно от UI.

---

### 6. Декоратор (Decorator)

- **Класс:** `TimedCommandDecorator implements Command`
  - принимает `Command` и `MetricsCollector`;
  - в `execute()`:
    - замеряет время выполнения целевой команды;
    - отправляет результат в `MetricsCollector`.

- **Где используется:**
  - в `ConsoleApplication`: вместо прямого вызова `command.execute()` используется:
    - `new TimedCommandDecorator(command, metricsCollector).execute()`.

**Зачем:**

- добавить измерение времени выполнения сценария, не модифицируя код самих команд;
- возможность расширять функциональность команд (например, добавить логирование, retry и т.д.) через новые декораторы.

---

### 7. DI-контейнер (Spring)

Не классический GoF-паттерн, но важный архитектурный элемент:

- `AppConfig` (`@Configuration`, `@Bean`, `@ComponentScan`) строит граф объектов:
  - репозитории, фабрика, сервисы, фасады, импортеры, экспортёры, метрики;
- `Main` поднимает Spring-контекст и получает `ConsoleApplication` как бин.

**Зачем:**

- отделить конфигурацию зависимостей от бизнес-логики;
- обеспечить возможность подмены реализаций (например, in-memory репозиториев на реальную БД) без переписывания остального кода.

## Итог

В решении:

- реализована доменная модель для модуля «Учет финансов» (счета, категории, операции);
- покрыты обязательные и часть опциональных требований (аналитика, импорт/экспорт, пересчёт балансов, метрики сценариев);
- используются паттерны GoF (Factory, Facade, Template Method, Visitor, Command, Decorator);
- соблюдены принципы SOLID и GRASP;
- используется DI-контейнер Spring для сборки приложения.

Это позволяет продемонстрировать не только работающее решение, но и грамотную архитектуру с упором на паттерны проектирования.
